## Answer

Requests switched its default text-encoding detector from **chardet** to **charset_normalizer** for **licensing reasons**: chardet is LGPL-licensed, while charset_normalizer is MIT-licensed. Using an LGPL dependency made the license status of downstream projects that bundle/vendor requests ambiguous, so requests replaced it with an MIT equivalent. chardet was kept only as an optional "escape hatch" that is used if it happens to be installed, but it is no longer a hard dependency.

### Supporting commit

**`2ed84f55b22f19a1e1e8eea2e50963dce62052d3`** — *"Switch LGPL'd chardet for MIT licensed charset_normalizer (#5797)"* (Ash Berlin-Taylor, 2021-07-07). Verified as an ancestor of the pinned HEAD `dae7ef63`.

From the commit message:

> Although using the (non-vendored) chardet library is fine for requests itself, but using a LGPL dependency the story is a lot less clear for downstream projects, particularly ones that might like to bundle requests (and thus chardet) in to a single binary -- think something similar to what docker-compose is doing. By including an LGPL'd module it is no longer clear if the resulting artefact must also be LGPL'd.
>
> By changing out this dependency for one under MIT we remove all license ambiguity.
>
> As an "escape hatch" I have made the code so that it will use chardet first if it is installed, but we no longer depend upon it directly, although there is a new extra added, `requests[lgpl]`. ...

The modern tree still reflects this: `pyproject.toml` requires `charset_normalizer>=2,<4`, keeps `use_chardet_on_py3 = ["chardet>=3.0.2,<8"]` as an optional extra, and `requests/compat.py` resolves `chardet` first, falling back to `charset_normalizer`.
