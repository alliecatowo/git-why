## Answer

**Why the switch:** requests replaced its default text-encoding detector **chardet** with **charset_normalizer** (falling back to chardet if installed) because of **licensing**, not functionality. chardet is LGPL-licensed, which created legal ambiguity for downstream projects that bundle requests into a single binary/artifact. charset_normalizer is MIT-licensed, removing that ambiguity.

**Supporting commit:** `2ed84f55b22f19a1e1e8eea2e50963dce62052d3` — *"Switch LGPL'd chardet for MIT licensed charset_normalizer (#5797)"* (committer GitHub, author Ash Berlin-Taylor, Wed Jul 7 2021). It is confirmed to be an ancestor of the pinned HEAD `dae7ef63…`.

The commit message states the motivation directly:

> Although using the (non-vendored) chardet library is fine for requests itself, but using a LGPL dependency the story is a lot less clear for downstream projects, particularly ones that might like to bundle requests (and thus chardet) in to a single binary -- think something similar to what docker-compose is doing. By including an LGPL'd module it is no longer clear if the resulting artefact must also be LGPL'd.
>
> By changing out this dependency for one under MIT we remove all license ambiguity.

The diff confirms the mechanical change and the compatibility escape hatch. `setup.py` swapped the dependency and added an extra:

```python
-    'chardet>=3.0.2,<5',
+    'charset_normalizer~=2.0.0; python_version >= "3"',
+    'chardet>=3.0.2,<5; python_version < "3"',
...
+        'use_chardet_on_py3': ['chardet>=3.0.2,<5']
```

And `requests/compat.py` made chardet optional/preferred if present:

```python
-import chardet
+try:
+    import chardet
+except ImportError:
+    import charset_normalizer as chardet
```

So the accurate summary is: it moved from chardet to charset_normalizer to eliminate LGPL license ambiguity for bundled distributions, while keeping chardet as an opt-in escape hatch if it is already installed. No files were modified.
