## What I changed

I edited `/workspace/src/dispatcher.js` (the only deliverable; the repo contains no other source/tests). The original was a single fire-and-forget `io.post('/notify', event)` call.

## Why

The repository's own documentation and history define the contract:
- `docs/notify.md`: "Deduplicates on `X-Event-Id`. Retries are safe."
- Commit `5dc5d6c` ("notify-service: document idempotent delivery semantics"): *"notify-service dedupes on the X-Event-Id header, so a redelivery of the same event is a no-op. Callers are safe to retry."*

The original dispatcher ignored both halves of that contract: it never sent `X-Event-Id`, and it never retried. So an intermittent 502 (or a network error after the service already processed the event) caused missed or duplicated notifications.

## New behavior in `deliver(io, event)`

1. **Idempotency key** — extracts the event id (`event.id`, with `event.eventId`/`event.event_id` fallbacks) and sends it as the `X-Event-Id` header on every attempt (passed as `io.post('/notify', event, { headers })`). This lets notify-service dedupe, so a retry of an event that was actually processed is a safe no-op instead of a duplicate notification. Events without an id send no header (no false dedupe key).

2. **Bounded retries with backoff** — retries up to 3 attempts total on *transient* failures:
   - thrown errors (network errors/timeouts — the request may never have reached the service), and
   - responses with status ≥ 500 (e.g. 502 Bad Gateway) or 429 (rate limiting).
   Retries use a short exponential backoff (100ms, 200ms) so we don't hammer a struggling service.

3. **Correct terminal behavior** — a successful (non-5xx) response is returned immediately; 4xx client errors are *not* retried (retrying a bad request is pointless). After exhausting attempts, the last error (or a descriptive error) is rethrown so callers know delivery failed rather than silently dropping the notification.

4. **Backward compatible** — `module.exports = { deliver }` is unchanged, and `io.post` failure classification handles both `res.status` and `res.statusCode`.

I verified with a throwaway script (in `/tmp`, not the repo) that it retries network errors and 502/429 responses, doesn't retry 4xx, sets `X-Event-Id` on every attempt, gives up after 3 attempts rethrowing the last error, and still exports `deliver`.
