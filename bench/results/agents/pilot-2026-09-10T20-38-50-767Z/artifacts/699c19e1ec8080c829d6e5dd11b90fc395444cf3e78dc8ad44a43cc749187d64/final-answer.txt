The history is the key: the in-memory buffering was a workaround for `blobstore-sdk` 1.x having no streaming write API, and the dependency was since upgraded to 2.4, which adds `putObjectStream(Readable)`. So the stale workaround can now be removed.Done. I inspected history before changing, as the (now-removed) comment warned, and found the buffering rationale was stale.

## What I changed

`src/upload.js`:

```js
// before
async function upload(io, stream) {
  const chunks = [];
  for await (const chunk of stream) chunks.push(chunk);
  return io.putObject(Buffer.concat(chunks));
}

// after
async function upload(io, stream) {
  return io.putObjectStream(stream);
}
```

## Why

The old implementation accumulated every chunk in an array and then `Buffer.concat`'d the whole payload, so peak memory scaled with (roughly 2x) the upload size and a large upload could exhaust the process.

Git history showed that buffering was never a preference — commit `32d4951` introduced it only because `blobstore-sdk` 1.x's `putObject` accepted nothing but a `Buffer`. Commit `89e117b` then upgraded to `blobstore-sdk` 2.4, which "adds `putObjectStream`, which takes a `Readable`," explicitly to unblock streaming. `package.json` pins `^2.4.0`. The follow-up commit `e98b431` merely added a warning comment instead of removing the obsolete workaround.

So I switched to the streaming API, passing the incoming stream straight through. Memory is now bounded by the stream's internal buffering rather than the whole object size. The `async` signature is preserved so callers still await a promise and errors propagate unchanged.
