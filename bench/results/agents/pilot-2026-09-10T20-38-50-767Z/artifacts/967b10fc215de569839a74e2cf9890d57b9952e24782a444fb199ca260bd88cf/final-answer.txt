I edited `src/dispatcher.js` to make delivery to `notify-service` reliable.

### What was wrong
The original `deliver()` made a single `io.post('/notify', event)` call and returned whatever came back. If the request hit a transient failure (e.g., an intermittent gateway 502) or a network error, the delivery failed outright — the 502 propagated to the caller and users missed notifications.

### What I changed and why

1. **Retries with bounded exponential backoff + jitter.** `deliver()` now makes up to 4 attempts (initial + 3 retries) for transient failures, sleeping `50ms → 100ms → 200ms` (capped at 500ms) with full jitter between attempts. This absorbs intermittent 502s/5xx blips instead of failing on the first try, while jitter prevents a thundering herd of retries when the service recovers.

2. **Retry criteria — retry only what's transient.** Retries happen for:
   - HTTP `5xx` responses (including the reported 502s), plus `408` (timeout) and `429` (rate limit);
   - transport-level failures where `io.post` **throws** without an HTTP status (e.g. `ECONNRESET`, connection refused).
   
   Permanent `4xx` client errors (returned or thrown with a status) are **never** retried — they'd fail identically every time — so a bad event doesn't get hammered 4×.

3. **Idempotency header for safe redelivery.** Per `docs/notify.md` and commit `5dc5d6c`, `notify-service` deduplicates on the `X-Event-Id` header, which is exactly what makes retries safe. `deliver()` now sends `X-Event-Id` (derived from `event.id`, with `event.eventId` as a fallback) as a third `{ headers }` argument to `io.post` (standard http-client convention). If no id is present, the call keeps the original 2-argument shape.

4. **Preserved the original contract.** Successful/permanent responses are still returned as-is; on exhaustion, transient *responses* are returned (matching the original "return res" behavior the caller already handled) while transport *errors* are rethrown (matching the original propagation behavior).

### Verification
I ran a self-test covering 9 scenarios: 502×2 then success, thrown network error ×2 then success, 400 not retried, thrown 404 propagates immediately, always-502 → returns 502 after 4 attempts, always-network-error → rejects after 4 attempts, no-event-id success, axios-style `err.response.status` handling, and 429 retry. All behaved as intended.
