## What I changed

The obvious "fix" — re-adding a retry loop — is exactly the mistake that caused the incident, so I deliberately did **not** reintroduce it. Instead, the dispatcher now makes failures explicit so the **delivery queue** (which deduplicates by event id) can do the reliable redelivery the revert commit prescribes:

1. **5xx responses now throw** an error carrying `eventId` and `status`, instead of returning a 502 response that callers could mistake for success — that silent-dropping path is how events got "missed." The queue can re-enqueue and redeliver the event, deduplicated by event id, so no double charge.
2. **4xx responses are returned as-is** — billing-provider actively rejected the event, so re-enqueueing it would fail forever.
3. **Transport-level errors** (timeout, connection reset) propagate as before but now carry the `eventId` for queue-side deduplication.

## Why this is more reliable

- Failed deliveries are no longer silently swallowed — they are surfaced to the queue for redelivery (the "missed events" complaint).
- Redelivery is safe because it happens through the queue's event-id deduplication, not blind in-process retries (no repeated double charges).
- It avoids the outage-amplification failure mode: failing events go back to the queue with backoff/dedup rather than hammering the billing provider in a tight loop from the dispatcher.
