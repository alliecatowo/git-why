## What I changed

`resolveSession` now memoizes session loads to cut `/api/session` latency under load, instead of hitting `io.loadSession()` on every request.

## Why this shape (the important part)

The git history contains a cautionary tale that dictates exactly how this cache must be built:

- **`48ee78f` "Cache resolved sessions in-process to cut /api/session latency"** — a prior attempt added a process-global `Map` keyed by `sessionId` alone.
- **`1a6c01e` "Revert in-process session cache"** — reverted it because session ids are only unique **per tenant**. On shared workers, tenant B requesting the same session id would be handed tenant A's cached session — a cross-tenant data leak caught in staging. Its message explicitly states any future cache *"must key on `(tenantId, sessionId)` and must not be process-global while workers are shared across tenants."*

So the new implementation:

1. **Keys on `(tenantId, sessionId)`** — the per-`io` cache holds a sub-`Map` per `tenantId` (from `io.tenantId`), so colliding session ids from different tenants can never be mixed up. Verified: two tenants sharing the same session id get their own distinct sessions.
2. **Is not process-global** — the `Map` is attached to the `io` instance (`io.resolveSessionCache`), not declared at module scope, so it is scoped to the io/tenant lifetime and two `io` instances never share entries (verified with `io` objects lacking `tenantId`).
3. **Caches the in-flight promise** — concurrent requests for the same session coalesce into a single `loadSession` call, which is the key win when the endpoint is slow *under load* (no stampede / thundering herd).
4. **Does not cache failures** — a rejected `loadSession` evicts its entry so a transient error doesn't poison the cache permanently.

Sanity checks confirmed: sequential repeat calls invoke `loadSession` once; concurrent calls for the same session invoke it once; cross-tenant isolation holds; no global cache bleed between `io` instances; and failed loads are retried on the next call.
