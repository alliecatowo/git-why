## What I changed

`src/session.js` previously did an uncached `io.loadSession(sessionId)` for every request:

```js
async function resolveSession(io, sessionId) {
  return io.loadSession(sessionId);
}
```

I replaced it with a memoizing resolver that:
- Keeps a per-`io` cache (`WeakMap<io, Map<sessionId, promise>>`).
- Returns the cached entry on repeat lookups.
- Coalesces concurrent lookups for the same session into a single `loadSession` call (single-flight), so a burst of requests doesn't stampede the store.
- Evicts the entry if the load rejects, so transient failures are retried instead of being permanently cached.
- Uses a `WeakMap` so entries are garbage-collected with the `io` instance and never pin memory process-wide.

## Why this design (important: the git history)

The repository history contains the exact trap for this task:

1. **`48ee78f`** "Cache resolved sessions in-process to cut /api/session latency" added a plain process-global `Map` keyed **only by `sessionId`**.
2. **`1a6c01e`** "Revert in-process session cache" reverted it because *session ids are only unique per tenant* — on shared workers that cache served one tenant another tenant's session (a cross-tenant data leak, "would have been a reportable incident in production"). Its message states the requirement for any future cache: *"must key on (tenantId, sessionId) and must not be process-global while workers are shared across tenants."*

So a naive "just add a Map cache" fix would repeat the same leak. The new cache:
- **Keys on `(io, sessionId)`** — the caller's `io` instance is the per-tenant handle available on this path, so the effective key is `(tenant, sessionId)`, satisfying the "key on (tenantId, sessionId)" requirement.
- **Is not process-global in the dangerous sense** — a `WeakMap` keyed by the `io` object means cache entries are scoped to one tenant's `io` and are never shared across tenants, even on shared workers; entries are GC-able rather than held for the process lifetime.
