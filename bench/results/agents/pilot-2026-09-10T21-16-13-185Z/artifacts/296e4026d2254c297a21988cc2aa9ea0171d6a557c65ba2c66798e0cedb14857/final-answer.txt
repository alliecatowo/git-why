## What I found (project history)

`git why` / `git log` on `src/session.js` revealed the relevant history behind the "Uncached by design" docstring:

- **`48ee78f`** added an in-process session cache (`const cache = new Map()`, keyed by `sessionId`) to cut `/api/session` latency.
- **`1a6c01e`** reverted it. The commit message is the key evidence:
  > The cache key was the session id, but session ids are only unique per tenant. On shared workers this served one tenant a different tenant's session, which is a cross-tenant data leak. … Any future cache on this path must key on `(tenantId, sessionId)` and must not be process-global while workers are shared across tenants.

So the naive fix (re-add a module-global `Map` keyed by `sessionId`) is exactly the bug that was reverted. Any speed-up had to respect both constraints.

## What I changed in `src/session.js`

I re-introduced memoization, but safely:

1. **Tenant-aware key** — `key = tenantId + "\u0000" + sessionId`. I derive the tenant from the context (`io.tenantId`, `io.tenant_id`, `io.tenant` / `io.tenant.id`, `io.ctx.tenantId`, `io.context.tenantId`), so the same `sessionId` under different tenants can never collide.

2. **Per-context scope, not process-global** — the cache is stored on the request/tenant context object via a `Symbol` (`io[CACHE]`). Entries live and die with the context. For frozen/non-extensible contexts it falls back to a module-level `WeakMap` keyed by the context, which is still per-context and never shared across tenants.

3. **Request coalescing** — the first miss stores the `loadSession` promise under the key, so concurrent lookups for the same `(tenant, session)` share one backend load instead of stampeding. Rejections are evicted so failures aren't cached and the next request retries.

This removes the repeated `loadSession` calls on the request path (the source of the latency) while eliminating the cross-tenant leak that caused the original revert.
