## What I changed

The original `deliver()` was a single fire-and-forget `POST` with no retry and no idempotency header — so any transient 502 permanently dropped the notification. The repo's own `docs/notify.md` (added in commit `dca6906`) states: *"notify-service Deduplicates on `X-Event-Id`. Retries are safe."* I built the fix around those two facts:

1. **Idempotent redelivery (`X-Event-Id` header)** — the dispatcher now sends the event's id (`event.id`, with `event.eventId` fallback) as the `X-Event-Id` header on every attempt. Since the service dedupes on this header, retries are safe no-ops rather than duplicate notifications.

2. **Retry with exponential backoff + jitter** — transient failures (5xx including the intermittent 502, 429, and network-level errors like connection refused/timeout) are retried up to 5 attempts (configurable via `options.maxAttempts`), with exponential backoff (100ms base, 5s cap) plus up to 25% jitter to avoid thundering-herd retries. A numeric `Retry-After` response header is honored when present.

3. **No wasted retries on permanent failures** — 4xx client errors (other than 429) are returned immediately, since retrying won't fix them.

4. **Clear failure semantics** — after exhausting attempts on HTTP errors, the last response is returned (preserving the original "return `res`" contract so callers can still inspect `res.status`); on persistent network errors it rethrows the last error so the failure isn't silently swallowed (the root cause of "missed notifications").
