## What I changed

`src/dispatcher.js` previously made a single fire-and-forget POST to `/notify` with no retry handling, so any intermittent 502 (or transient network error) caused a missed notification. I added bounded retry logic:

1. **Retries transient failures** — 5xx responses (the reported 502s, plus 503/504), 429 rate-limit responses, and network-level errors (`ECONNRESET`, `ECONNREFUSED`, `ETIMEDOUT`, `EAI_AGAIN`, socket hangs, etc.).
2. **Does not retry permanent failures** — 4xx client errors are returned to the caller immediately (retrying them would be pointless and wasteful).
3. **Exponential backoff with jitter** — base 100ms, doubling per attempt, capped at 5s, with random jitter to avoid a thundering herd when notify-service recovers.
4. **Honors `Retry-After`** when the response provides one (capped at the max backoff so a bad header can't stall delivery).
5. **Bounded attempts** — default 3 attempts (configurable via `deliver(io, event, { maxAttempts })`), so a truly down service doesn't cause unbounded hangs; the last response is returned (or the last error thrown) after the budget is exhausted.
6. **Backward compatible** — same `deliver(io, event)` signature and same `{ deliver }` export; handles both `res.status` and `res.statusCode` response shapes.

## Why this is safe

`docs/notify.md` states: *"Deduplicates on `X-Event-Id`. Retries are safe."* — notify-service treats a redelivery of the same event as a no-op, so re-sending on transient failure cannot produce duplicate notifications. Retrying is therefore the intended, safe way to close the 502-driven reliability gap and stop missed notifications.

I verified the change with a local test harness covering: immediate success, 502→success retry, network-error→success retry, 4xx non-retry, persistent-502 bounded attempts, persistent-network-error throw, non-transient error no-retry, `statusCode`-style responses, `Retry-After` handling, and custom `maxAttempts` — all passed.
