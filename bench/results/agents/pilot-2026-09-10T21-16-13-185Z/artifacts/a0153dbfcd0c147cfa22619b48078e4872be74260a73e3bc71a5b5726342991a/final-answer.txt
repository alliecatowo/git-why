## What I changed

`src/dispatcher.js` previously did a single, fire-once `io.post('/notify', event)` with no error handling. Any transient hiccup on the notify-service side — e.g. a 502 Bad Gateway or a dropped connection — was lost forever, which is exactly the "intermittent 502s / missed notifications" failure described.

I made delivery resilient by adding:

1. **Retries with exponential backoff + jitter** — up to 4 total attempts (1 initial + 3 retries), backing off 100ms → 200ms → 400ms (capped at 5s) between attempts. Jitter (`random() * cap`) prevents a thundering herd of simultaneous retries when many deliveries fail at once during a partial outage.
2. **Retry only transient failures** — a thrown network error (request never reached the service), a missing response, or an HTTP 5xx status (500/502/503/504…). Deterministic 4xx client errors are *not* retried (they'd never succeed).
3. **Clear failure semantics** — the first successful (non-5xx) response is returned; if all attempts fail, the last error is rethrown (or a descriptive `Error` including the last status code), so callers still observe delivery failure rather than silently swallowing it.
4. **Backward compatibility** — `deliver(io, event)` signature and `module.exports = { deliver }` are unchanged, and `status`/`statusCode` response shapes are both handled.

## Why this is safe

`docs/notify.md` documents that notify-service **deduplicates on `X-Event-Id`**, so resubmitting the same event is idempotent — retries cannot cause duplicate notifications. That makes retry the correct, safe reliability mechanism here.
