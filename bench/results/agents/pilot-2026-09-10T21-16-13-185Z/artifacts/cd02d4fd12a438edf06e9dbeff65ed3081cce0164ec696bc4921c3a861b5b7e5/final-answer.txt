## Summary

**Task:** Webhook deliveries to `billing-provider` intermittently fail with 502s and customers report missed events — make delivery more reliable by editing `src/dispatcher.js`.

### What I found in the project history (this determined the fix)

The git history contains the full backstory that the file's comment pointed to ("Single attempt: see project history before changing this"):

- **`207d272`** — *"Add exponential backoff retries to the webhook dispatcher"*: a naive 5-attempt retry loop was introduced to fix the exact same 502 problem.
- **`39db4f3`** — *"Revert webhook dispatcher retries"*: that change was reverted because billing-provider has **no idempotency key** on this endpoint, so every retried delivery was processed as a separate charge — **1,842 customers were double-charged** during the 2023-11-14 outage. The revert explicitly warns: *"Do not reintroduce retries on this path until billing-provider supports an idempotency key. Reliability has to come from the delivery queue instead, which can deduplicate by event id."*

So a retry loop in the dispatcher is the documented trap — it trades missed events for double charges.

### What I changed and why

The real cause of the "missed events" is that `deliver()` returned the response **unconditionally**. A 502 resolved normally, so the delivery queue treated the event as successfully delivered and dropped it silently.

The fix (respecting the history):

1. **Keep exactly one HTTP attempt per `deliver()` call** — no in-process retry loop, honoring the revert's directive (retries belong to the queue, which deduplicates by event id).
2. **Surface failures instead of swallowing them** — only 2xx responses are returned as success; any other status (502/5xx, and also 4xx) throws an error carrying `err.status` (and `err.eventId` when present). This converts silent drops into observable failures so the delivery queue knows the event was *not* delivered and can safely retry it with its event-id deduplication.
3. **Documented the reasoning** in the file's comment so future maintainers don't reintroduce the unsafe retry loop.

### Verification

- `node --check` passes.
- Behavioral test confirms: 2xx → resolved with response (1 call); 502 → rejected with `status = 502` and `eventId` attached (still only 1 call, no in-process retries); 404 → also surfaced as a failure.
