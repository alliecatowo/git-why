## What I changed

The original `deliver()` made a single `await io.post('/notify', event)` with no retry handling, so any transient 502 (or network blip) permanently lost the notification. I replaced it with a retry loop that:

1. **Retries transient failures up to 5 attempts** — using `isRetryable()` to distinguish transient failures (no response / network errors, 5xx, and 429 rate limits) from permanent client errors (4xx), which are returned immediately without wasteful retries.
2. **Exponential backoff with full jitter** — delay = `random(0, BASE_DELAY * 2^attempt)`, capped at 5s. This spaces out retries so a recovering notify-service isn't hit by a thundering herd, and jitter avoids synchronized retry waves.
3. **Preserves the original interface** — `deliver(io, event)` still returns the successful response on success, or the last failure (response/error) if all attempts are exhausted, so callers can observe/dedupe failures rather than having a silent loss.
4. Handles both `res.status` and `res.statusCode` response shapes.

## Why this is safe

`docs/notify.md` explicitly states: *"Deduplicates on `X-Event-Id`. Retries are safe."* So re-POSTing the same event is idempotent — the notify-service won't deliver duplicates — which makes retry the correct and intended reliability mechanism here. I added a comment noting this in the file.
