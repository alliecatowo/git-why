## Answer

**The bug (CVE-2022-27774):** When curl followed an HTTP redirect (`Location:` header) that pointed to a different port or a different protocol/scheme on the same host, it would continue sending the previously-set HTTP Basic/Digest/etc. authentication credentials (username/password) to that new destination. This allowed a malicious or compromised server to redirect a client to another service (different port or protocol) and harvest the user's credentials.

**The fix:** Commit **`620ea21410030a9977396b4661806bc187231b79`** ("transfer: redirects to other protocols or ports clear auth") in `lib/transfer.c`, inside `Curl_follow()`. It added logic that, unless the user has explicitly opted in (`data->set.allow_auth_to_other_hosts`), compares the port and protocol of the redirect target against the original connection's port/protocol, and if either differs, it clears (frees) the stored auth credentials before following the redirect:

```
+    /* Clear auth if this redirects to a different port number or protocol,
+       unless permitted */
+    if(!data->set.allow_auth_to_other_hosts && (type != FOLLOW_FAKE)) {
...
+      if(port != data->info.conn_remote_port) {
+        infof(data, "Clear auth, redirects to port from %u to %u",
+              data->info.conn_remote_port, port);
+        clear = TRUE;
+      }
+      else {
...
+        if(p && (p->protocol != data->info.conn_protocol)) {
+          infof(data, "Clear auth, redirects scheme from %s to %s",
+                data->info.conn_scheme, scheme);
+          clear = TRUE;
+        }
...
+      if(clear) {
+        Curl_safefree(data->state.aptr.user);
+        Curl_safefree(data->state.aptr.passwd);
+      }
```
