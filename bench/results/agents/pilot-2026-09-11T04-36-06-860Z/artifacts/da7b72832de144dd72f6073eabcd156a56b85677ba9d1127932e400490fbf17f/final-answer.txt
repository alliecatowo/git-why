## Answer

**Yes** — `requests` originally used `chardet` (LGPL-licensed) as its default character/text-encoding detection library, and it switched to `charset_normalizer` (MIT-licensed) as the new default.

### Reason for the switch (quoted from commit message)

> Although using the (non-vendored) chardet library is fine for requests itself, but using a LGPL dependency the story is a lot less clear for downstream projects, particularly ones that might like to bundle requests (and thus chardet) in to a single binary -- think something similar to what docker-compose is doing. By including an LGPL'd module it is no longer clear if the resulting artefact must also be LGPL'd.
>
> By changing out this dependency for one under MIT we remove all license ambiguity.
>
> As an "escape hatch" I have made the code so that it will use chardet first if it is installed, but we no longer depend upon it directly, although there is a new extra added, `requests[lgpl]`. This should minimize the impact to users, and give them an escape hatch if charset_normalizer turns out to be not as good.

### Summary

The motivation was **licensing**, not detection quality: `chardet` is LGPL-licensed, which creates ambiguity for downstream projects that want to bundle `requests` into single-binary distributions (the commit cites `docker-compose`-style bundling as an example) — an LGPL dependency can force the whole bundled artifact to be LGPL-licensed. Switching the default to the MIT-licensed `charset_normalizer` removes that ambiguity, while still allowing `chardet` to be used as a fallback/opt-in via the `requests[lgpl]` (later `use_chardet_on_py3`) extra for backward compatibility. I found no indication in this commit or its message that detection accuracy was the driving factor — the author even notes charset_normalizer detected the same encoding as chardet in all their tests.
