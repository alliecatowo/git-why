### What the fix changed

Before this commit, `Curl_follow()` in `lib/transfer.c` simply extracted the new URL and followed it; credentials stored in the easy handle (`data->state.aptr.user` / `.passwd`) survived the redirect as long as the *host name* was unchanged. The fix added a check in the redirect-handling path that also compares **port** and **protocol/scheme**, and wipes the stored credentials when either differs — unless the application has explicitly opted in via `CURLOPT_UNRESTRICTED_AUTH` (`data->set.allow_auth_to_other_hosts`). Key part of the diff (`lib/transfer.c`, additions marked `+`):

```c
+    /* Clear auth if this redirects to a different port number or protocol,
+       unless permitted */
+    if(!data->set.allow_auth_to_other_hosts && (type != FOLLOW_FAKE)) {
...
+      if(port != data->info.conn_remote_port) {
+        infof(data, "Clear auth, redirects to port from %u to %u",
+              data->info.conn_remote_port, port);
+        clear = TRUE;
+      }
+      else {
...
+        p = Curl_builtin_scheme(scheme);
+        if(p && (p->protocol != data->info.conn_protocol)) {
+          infof(data, "Clear auth, redirects scheme from %s to %s",
+                data->info.conn_scheme, scheme);
+          clear = TRUE;
+        }
...
+      if(clear) {
+        Curl_safefree(data->state.aptr.user);
+        Curl_safefree(data->state.aptr.passwd);
+      }
```

Notably, the port is taken from `CURLOPT_PORT` when a custom port is in effect, otherwise from the URL with `CURLU_DEFAULT_PORT` so scheme-default ports compare correctly. The diff touched only `lib/transfer.c` (48 insertions, 1 deletion).
