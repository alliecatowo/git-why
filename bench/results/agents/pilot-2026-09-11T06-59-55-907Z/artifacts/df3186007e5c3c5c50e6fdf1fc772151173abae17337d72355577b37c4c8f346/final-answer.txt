**Yes — requests switched its default encoding guesser from `chardet` to `charset_normalizer`, and the reason was software *licensing*, not technical quality.**

`chardet` is LGPL-licensed. That created license ambiguity for downstream projects that bundle/vendor requests (e.g. freezing into a single binary), so requests replaced the hard dependency with the MIT-licensed `charset_normalizer`.

### The commit that establishes this

**SHA `2ed84f55b22f19a1e1e8eea2e50963dce62052d3`** — "Switch LGPL'd chardet for MIT licensed charset_normalizer (#5797)", Ash Berlin-Taylor, 2021-07-07 (co-authored by Jarek Potiuk).

Quoting the commit message:

> Although using the (non-vendored) chardet library is fine for requests itself, but using a LGPL dependency the story is a lot less clear for downstream projects, particularly ones that might like to bundle requests (and thus chardet) in to a single binary -- think something similar to what docker-compose is doing. By including an LGPL'd module it is no longer clear if the resulting artefact must also be LGPL'd.
>
> By changing out this dependency for one under MIT we remove all license ambiguity.
>
> As an "escape hatch" I have made the code so that it will use chardet first if it is installed, but we no longer depend upon it directly... (In my non-exhaustive tests it detects the same encoding as chartdet in every case I threw at it)

And the diff itself, in `requests/compat.py`:

```diff
-import chardet
+try:
+    import chardet
+except ImportError:
+    import charset_normalizer as chardet
```

with `setup.py`:

```diff
-    'chardet>=3.0.2,<5',
+    'charset_normalizer~=2.0.0; python_version >= "3"',
+    'chardet>=3.0.2,<5; python_version < "3"',
...
+        'use_chardet_on_py3': ['chardet>=3.0.2,<5']
```

The same commit added the `HISTORY.md` note: "Instead of `chardet`, use the MIT-licensed `charset_normalizer` for Python3 to remove license ambiguity for projects bundling requests. If `chardet` is already installed on your machine it will be used instead of `charset_normalizer` to keep backwards compatibility."

### Two important nuances

1. **`chardet` still wins if present.** The switch changed the *declared dependency*, not an absolute preference. Today's `src/requests/compat.py` still probes `chardet` first, then `charset_normalizer`, and `pyproject.toml` retains the `use_chardet_on_py3 = ["chardet>=3.0.2,<8"]` extra for users who want the old behavior.

2. **Detection is now fully optional.** Follow-up commit `555b870eb19d497ddb67042645420083ec8efb02` ("Allow character detection dependencies to be optional in post-packaging steps", 2024-05-14) replaced the try/except with `_resolve_char_detection()`, which may return `None`. Per `HISTORY.md`: "Requests now supports optional use of character detection (`chardet` or `charset_normalizer`) when repackaged or vendored... `Response.text()` and `apparent_encoding` APIs will default to `utf-8` if neither library is present. (#6702)"

### Bonus historical trivia

This wasn't the first license-motivated swap. Commit `20f8027` (2013-11-01, "Chardet -> charade") moved to the `charade` fork, and `HISTORY.md` line 1362 records the later reversal: "Switch back to using chardet, since it has merged with charade."
