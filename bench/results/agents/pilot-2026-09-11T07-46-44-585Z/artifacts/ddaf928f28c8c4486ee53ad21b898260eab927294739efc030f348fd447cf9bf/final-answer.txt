## Final Summary

Based on my investigation of the ripgrep repository history using `git why` and direct commit examination, here are the answers to your six questions:

**1. What was that bug where using the same matching style for several patterns could skip one?**

When users passed duplicate patterns to ripgrep, the tool would waste time matching against the duplicates instead of deduplicating them first. Commit **88524a2** (core: dedup patterns) from 2023-10-10 addresses this by using a HashSet to dedup patterns by their concrete syntax, removing duplicate search cost entirely. The commit message states: "if the end user generated a list of, say, names and did not dedup them, then ripgrep could end up spending a lot of extra time on those duplicates if there are many of them."

**2. What was the bug where our curly-brace file filters stopped finding anything inside those bundled folders?**

The bug was that nested alternates in glob patterns (like `**/{node_modules/**/*/{ts,js},crates/**/*.{rs,toml}`) were not supported. Commit **5f5da48** (globset: support nested alternates) from 2025-05-12 by Luke Sandberg fixed this. The commit message explains: "I originally didn't add this I think for implementation simplicity, but it turns out that it really isn't much work to do." This prevented patterns with alternates inside bundled directory structures from working correctly.

**3. What was that slowdown on Windows from checking whether every single ignore file exists?**

Commit **a18cf6e** (ignore: add existence check for ignore files) from 2020-02-17 added a `.exists()` check before opening ignore files. However, the comment in the code notes: "until demonstrated otherwise, we speculatively do not do this on Windows since Windows is notorious for having slow file system operations." Later, commit **68b3c9e** (ignore: fetch directory entry metadata in batches) from 2026-07-09 addressed the Windows slowdown by fetching metadata in batches instead of checking each file individually, since "Windows prefers fetching metadata in batches."

**4. The thing where everyone just wanted paths given relative to the directory the command was set up for?**

Commit **924ba10** (test: fix `Command::current_dir` API) from 2025-10-11 addresses this by making the TestCommand API interpret paths relative to the directory the command was created for automatically, as the commit message states: "Every single call site wants to pass a path relative to the directory the command was created for. So just make it do that automatically, similar to `Dir::create` and friends."

**5. What was the bug that only started showing up after we moved past that earlier release?**

Commit **34edb81** (ignore: squash noisy error message) from 2020-03-16 fixed a regression introduced in version 12.0.0. The commit message explains: "This regression was introduced in #1446" and the changelog states it was "a regression introduced in the 12.0.0 release," where the code wasn't properly checking if the commondir file actually exists before trying to open it.

**6. How come search time hardly changed no matter how much trailing context you asked for?**

Commit **92dc402** (Switch from Docopt to Clap) from 2016-11-18 reveals that memory map searching disables itself when context is requested. The code shows: `Ok(if before > 0 || after > 0 || self.is_present("no-mmap") { false }`. This means that with trailing context, ripgrep falls back to streaming search rather than using the faster memory-mapped approach, which is why additional context has minimal performance impact—it was already using the slower streaming method.
