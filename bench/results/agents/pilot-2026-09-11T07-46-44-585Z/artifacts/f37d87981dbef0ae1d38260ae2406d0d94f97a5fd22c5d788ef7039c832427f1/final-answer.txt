### 2. Why were non-English filenames getting corrupted on Windows builds?

Non-English filenames were getting corrupted on Windows because invalid file name characters were not being handled properly when extracting filenames from Content-Disposition headers or other sources. The fix added character sanitization for Windows file names to replace or remove invalid characters before creating files.

**Commit:** e49d928 (2009-10-17) - "Fix invalid file name characters handling on Windows" - Bug report #2866724 indicated that curl on Windows failed when writing files whose file names originally contained characters which are not valid for file names on Windows.

### 3. Why did upgrading the crypto library suddenly flood us with deprecation warnings?

When OpenSSL 3.0 was released, it deprecated certain functions (like DES, MD4, and ENGINE-related functions) that libcurl was using. Since there were no immediate replacements available, the upgrade suddenly generated many deprecation warnings in the build. To fix this, the OPENSSL_SUPPRESS_DEPRECATED preprocessor flag was used to suppress these warnings.

**Commit:** 02174e4 (2020-03-25) - "openssl: adapt to functions marked as deprecated since version 3 - OpenSSL 3 deprecates SSL_CTX_load_verify_locations and the MD4, DES functions we use. Fix the MD4 and SSL_CTX_load_verify_locations warnings."

### 4. What was the case that only worked when we knew the length up front?

In HTTP/2 uploads, certain optimizations required knowing the content length upfront. When the content length was not known in advance (state.infilesize == -1), the code would handle data sending without specifying the data amount upfront by setting upload_left to -1 (unknown).

**Commit:** 03bb481 (2016-09-05) - "http2: skip the content-length parsing, detect unknown size" - Shows the code: `if(conn->data->state.infilesize != -1) stream->upload_left = conn->data->state.infilesize; else /* data sending without specifying the data amount up front */ stream->upload_left = -1;`

### 5. What was that test calling the memory-free helper that newer compilers kept flagging under strict warning flags?

Unit test 1302 was calling the memory-free helper Curl_safefree() to properly free memory from base64 encoding/decoding functions. Switching from plain free() to Curl_safefree() ensured proper pointer nullification and compatibility with stricter compiler warnings and memory debugging tools.

**Commit:** ebb9c7a (2011-01-05) - "Made unit_setup() return an error code to abort the test early - Also use Curl_safefree() in unit test 1302 so it will pass the memory torture test"

### 6. What was that thing that made it safe to call the header accessors in a loop without the returned values getting trashed?

The header accessor functions (curl_easy_header and curl_easy_nextheader) were modified to use separate storage buffers for each return value instead of sharing a single struct. This allows applications to call both functions in a loop without having the returned pointers get overwritten by subsequent calls.
