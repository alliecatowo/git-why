# Engineering Brief: `burntsushi-ripgrep` History & Design Decisions

### 1. What was the bug where the manual page rendered an odd-looking dash under certain doc tools?
* **Answer:** In unescaped roff documents, standard hyphens in command-line flags are often rendered as special Unicode hyphens (such as en-dashes or true hyphens) by certain doc renderers and manual page viewers. This made the dashes look odd and, more importantly, prevented users from successfully searching for those flags within their manual page viewer since they weren't standard ASCII hyphens. The issue was resolved by replacing `-` in flag names with the escaped `\-` roff sequence.
* **Commit SHA:** `74959a14cbcce19e2471b0d281ea5cdbd248527d`
* **Citing Quote (from commit message):**
  > *"Apparently, if we don't do this, some roff renderers with use a special Unicode hyphen. That in turn makes searching a man page not work as one would expect."*

### 2. What was that dependency we bumped so the thing would finally build on that router firmware?
* **Answer:** The repository switched its musl target allocator dependency from `jemallocator` to `tikv-jemallocator`. This bump/switch resolved a compilation failure on `riscv64gc-unknown-linux-musl`, which was a blocker for building and packaging ripgrep for OpenWrt (a Linux operating system/firmware widely used for routers).
* **Commit SHA:** `53279db4143f4307c2b1b27f2cd32a43b0496205`
* **Citing Quote (from commit message):**
  > *"It is now a recommended crate for jemalloc and it contains an [important fix for compilation on riscv64gc-unknown-linux-musl][fix], I bumped into this when I was trying to [build ripgrep on OpenWrt][openwrt]."*

---

### 3. What was that thing we got rid of because it kept breaking and caused nothing but trouble?
* **Answer:** The `simd-accel` Cargo build feature (and its underlying dependency on the `packed_simd` crate) was completely removed. It was used to speed up UTF-16 transcoding via the `encoding_rs` crate, but because it relied on unstable nightly Rust compiler APIs, it was prone to frequent compilation breakage.
* **Commit SHA:** `e9abbc1a02de29dbe60e1b625d540c58759b23a6`
* **Citing Quote (from commit message):**
  > *"cargo: nuke 'simd-accel' from orbit"*
  > *"This feature causes nothing but problems and is frequently broken."*

---

### 4. Why did all the bundled executables get resolved eagerly when running on Windows?
* **Answer:** Eager resolution of decompression and preprocessing helper binaries (such as `xz` or `gzip`) was introduced to fix a security vulnerability (CVE-2021-3013). On Windows, invoking a sub-process via `CreateProcess` with a relative path causes it to implicitly search the current working directory first. If a user searched an untrusted directory tree containing a malicious executable with the same name, it could lead to arbitrary program execution. Eagerly resolving the binaries to their absolute paths using `PATH` mitigated this risk.
* **Commit SHA:** `229d1a8d41b0023420e7815578fa0b39c0d5c2e4`
* **Citing Quote (from commit message):**
  > *"The root cause of this problem is that 'CreateProcess' on Windows will implicitly look in the current working directory for an executable when it is given a relative path to a program. Rust's standard library allows this behavior to occur, so we work around it here. We work around it by explicitly resolving programs like 'xz' via 'PATH'. That way, we only ever pass an absolute path to 'CreateProcess', which avoids the implicit behavior of checking the current working directory."*

### 5. What was the bug where names ending in two dots were treated as though they had no filename at all?
* **Answer:** Inside the `globset` crate's `pathutil::file_name` helper function, any path whose last byte was a dot (including paths ending in two dots like `asdf..`) was matched by an incorrect check and returned `None`. This caused the function to treat filenames ending in double-dots as having no filename at all. The fix replaced this blanket check to only return `None` on empty paths and paths ending specifically in `..`.
* **Commit SHA:** `4df1298127695ed1e76937f16de1a0135677ccf5`
* **Citing Quote (from commit message and diff):**
  > *"I'm not sure why I did this, but I think I was trying to imitate the contract of `std::path::Path::file_name` ... And as a result, if you have a glob that ends in a `.`, it was instead treated as the empty string (which only matches the empty string)."*
  > 
  > *From the diff in `crates/globset/src/pathutil.rs`:*
  > ```rust
  > -    if path.last_byte().map_or(true, |b| b == b'.') {
  > -        return None;
  > -    }
  > ```

### 6. What was the bug where capping the number of results could not be trusted anymore once surrounding lines were added to multi-line spellings?
* **Answer:** Previously, the `printer` crate was in charge of tracking match counts and enforcing the `--max-count` (`max_matches`) limit. However, in multi-line search mode, matches can span multiple lines, and when context lines (`-A/--after-context`) were being printed, a matching line could be printed again as context, which reset/interfered with the match counter in the printer, causing ripgrep to print more matches than the limit. The bug was solved by completely removing the limit handling from the `printer` crate and moving it directly into the `searcher` crate (`grep-searcher`'s `Core` search loop).
* **Commit SHA:** `a6e0be3c909c5c09e5fb402c907f3beb88cfb4c4`
* **Citing Quote (from commit message):**
  > *"This is a bit of a brutal change, but I believe is necessary in order to fix a bug in how we handle the "max matches" limit in multi-line mode while simultaneously handling context lines correctly."*
  > 
  > *"The main problem here is that "max matches" refers to the shorter of "one match per line" or "a single match." In typical grep, matches *can't* span multiple lines, so there's never a difference. But in multi-line mode, they can. So match counts necessarily must be handled differently for multi-line mode."*
