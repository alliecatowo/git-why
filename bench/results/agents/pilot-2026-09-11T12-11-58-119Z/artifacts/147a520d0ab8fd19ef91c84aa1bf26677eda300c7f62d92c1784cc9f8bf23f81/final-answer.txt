## Engineering brief: decisions in `burntsushi-ripgrep` history

### 1. Manual page rendered an odd-looking dash under certain doc tools

**Answer:** The man page was generated with unescaped hyphens in flag names, so some roff renderers substituted a special Unicode hyphen, breaking text-searchability of the man page. The fix escapes every hyphen in flag names as `\-` in the roff output.

**Commit SHA:** `74959a14cbcce19e2471b0d281ea5cdbd248527d`
(author: `man: escape all hyphens in flag names`)

**Supporting line (message):**
> "Apparently, if we don't do this, some roff renderers with use a special Unicode hyphen. That in turn makes searching a man page not work as one would expect."

**Supporting line (diff):**
> `let name = flag.name_long().replace("-", r"\-");`

### 2. Dependency bumped so it would build on router firmware

**Answer:** Swapped the `jemallocator` dependency for `tikv-jemallocator`, which contains a fix for compilation on `riscv64gc-unknown-linux-musl` that blocked building ripgrep on OpenWrt routers.

**Commit SHA:** `53279db4143f4307c2b1b27f2cd32a43b0496205`

**Supporting line (message):**

**Answer:** The Snap packaging/installation route. Snap packages produced a stream of nonsensical/strange bug reports that couldn't be fixed (even with `--classic`), so Snap was dropped from the README and its own note was added to the issue template.

### 4. Why bundled executables got resolved eagerly when running on Windows

**Answer:** The decompression helper binaries (used by `-z/--search-zip`) were built/resolved eagerly for security reasons, and on Windows building that reader eagerly resolves those binaries' paths. The fix only constructs the decompression reader when `--search-zip` is actually enabled, making resolution lazy.

**Commit SHA:** `916415857f084e63efda03cf25a67fe7f6d24244`
(author: `core: don't build decompression reader unless we intend to use it`)

**Supporting line (message):**
> "Building it can consume resources. In particular, on Windows, the various binaries are eagerly resolved. ... The earger resolution was added later for security purposes. But the 'eager' part isn't actually necessary."

**Supporting line (diff, doc comment):**
> "We do this because building the reader can sometimes do non-trivial work (like resolving the paths of decompression binaries on Windows)."

### 5. Bug where names ending in two dots were treated as having no filename at all

**Answer:** `file_name` in `globset` returned `None` whenever a path's last byte was `.` (in a misguided attempt to imitate `std::path::Path::file_name`, which returns `None` only when the path terminates in `..`). This wrongly treated names with a trailing dot (e.g. globs/names ending in `.`/`..`) as having no filename, so a trailing-dot glob matched only the empty string. The fix makes only the exact `..` component yield `None`.

**Commit SHA:** `4df1298127695ed1e76937f16de1a0135677ccf5`
(author: `globset: fix bug where trailing `.` in file name was incorrectly handled`)

**Supporting line (message):**
> "I was trying to imitate the contract of [`std::path::Path::file_name`]: 'Returns None if the path terminates in `..`.' But the status quo clearly did not implement this. And as a result, if you have a glob that ends in a `.`, it was instead treated as the empty string (which only matches the empty string)."

**Supporting line (diff):**
> `-  if path.last_byte().map_or(true, |b| b == b'.') {` / `+  if got == &b".."[..] { return None; }`

---

### 6. Bug where capping results couldn't be trusted once surrounding lines were added to multi-line matches

**Answer:** With `-m/--max-count` plus `-U/--multiline` and context, too many matches were printed. The max-count limit was enforced in the printer, but in multi-line mode match counting and context expansion are handled by the searcher, so the printer's cap couldn't be honored. The fix moved "max matches" handling out of `grep-printer` and into `grep-searcher`.

**Commit SHA:** `a6e0be3c909c5c09e5fb402c907f3beb88cfb4c4`
(author: `searcher: move "max matches" from printer to searcher`, "Fixes #3076, Closes #3094")

**Supporting line (message):**
> "The main problem here is that 'max matches' refers to the shorter of 'one match per line' or 'a single match.' ... But in multi-line mode, they can. ... The printer was previously responsible for this. But for $reasons, the printer is fundamentally not in charge of how matches are found and reported."

**Supporting line (message):**
> "I believe is necessary in order to fix a bug in how we handle the 'max matches' limit in multi-line mode while simultaneously handling context lines correctly."
